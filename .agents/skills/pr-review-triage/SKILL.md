# PR Review Triage

既存の GitHub PR レビューコメントを集め、それぞれの指摘が現在のコード・実装方針に照らして妥当かどうかを判定し、対応要否の一覧表を作る。

このスキルは `code-review` プラグイン(`/code-review` コマンド)の「指摘の確信度を 0-100 でスコアリングし、false positive を弾く」というロジックをベースに、対象を「これから書くレビュー」ではなく「すでに投稿されたレビューコメント」に変えたもの。

## Step 1: 対象PRの特定

- 引数で PR 番号 / URL が指定されていればそれを使う。
- 指定がなければ、現在のブランチに紐づく PR を使う:
  ```
  gh pr view --json number,title,url,headRefName,baseRefName
  ```
- 複数候補がある、あるいは特定できない場合はユーザーに確認する。

## Step 2: レビューデータの取得(gh cli)

以下を組み合わせて、PR に付いた指摘を漏れなく集める。`OWNER/REPO` と `NUMBER` は Step 1 で得たものに置き換える。

1. **インラインのレビューコメント(diff の特定行に対する指摘)**
   ```
   gh api repos/OWNER/REPO/pulls/NUMBER/comments --paginate
   ```
   各要素に `path`(ファイル)、`line`/`original_line`、`body`(指摘内容)、`user.login`(レビュアー)、`diff_hunk`、`in_reply_to_id`(スレッド化されている場合)が含まれる。

2. **レビューのサマリ本文(Approve/Request changes/Comment 時に添えたコメント)**
   ```
   gh api repos/OWNER/REPO/pulls/NUMBER/reviews --paginate
   ```

3. **PR 全体に対する Issue コメント(diff に紐づかない指摘)**
   ```
   gh pr view NUMBER --comments
   ```
   または
   ```
   gh api repos/OWNER/REPO/issues/NUMBER/comments --paginate
   ```

4. **PR の diff(指摘対象コードの現在の状態を見るため)**
   ```
   gh pr diff NUMBER
   ```

5. **レビュースレッドの resolved 状態(GraphQL)**
   上記の REST エンドポイント(`pulls/.../comments` 等)のレスポンスにはスレッドの resolved 状態が含まれないため、resolved 状態を判定に使う場合は GraphQL で別途取得する:
   ```
   gh api graphql -f query='
     query($owner: String!, $repo: String!, $number: Int!) {
       repository(owner: $owner, name: $repo) {
         pullRequest(number: $number) {
           reviewThreads(first: 100) {
             nodes {
               isResolved
               comments(first: 100) { nodes { databaseId } }
             }
           }
         }
       }
     }' -F owner=OWNER -F repo=REPO -F number=NUMBER
   ```
   `comments.nodes[].databaseId` が Step 2-1 で取得したインラインコメントの `id` に対応するので、これで各コメントが属するスレッドの `isResolved` を突き合わせる。

同じスレッドに複数返信がある場合は、最新の状態(すでに解決済み・返信で反論されている等)を踏まえて1件の指摘として扱う。resolved 状態を判定理由に使う場合は上記の GraphQL クエリで確認した上で明記する。GraphQL を実行せず REST の情報だけで判定した場合は、resolved 状態は「未確認」として扱い、断定しない。

## Step 3: 判断材料の収集

各指摘を判定する前に、以下を確認する:

- **プロジェクトの実装方針**: リポジトリ直下および対象ファイルの親ディレクトリの `CLAUDE.md` を探して読む。存在しなければ、`README.md` や既存コードの一貫したパターンから方針を推測する。
- **指摘対象コードの現状**: 指摘されたファイル・行を実際に読む(Read)。指摘時点から変更されていないか、すでに別コミットで対応済みでないかを確認する。
- **実装意図の履歴**: 該当箇所が意図的な設計であることが多い場合は `git log -p` / `git blame` でその行が導入された経緯・コミットメッセージを確認する。
- **同種パターンの一貫性**: 同じ指摘がコードベースの他の箇所にも当てはまるか、それとも今回の箇所だけの特殊事情かを確認する。

## Step 4: 各指摘の判定

指摘ごとに、確信度を 0-100 で内部的に見積もり、`code-review` プラグインと同じ基準を使う:

- **0-25**: false positive。的外れ、または既存(pre-existing)の問題で今回のPRの範囲外。
- **26-50**: 根拠が弱い。指摘者の意図はわかるが、コード上・方針上それを裏付ける証拠がない、あるいは CLAUDE.md 等で明示的に求められていないスタイルの好み。
- **51-75**: 妥当だが影響は小さい。nitpick に近いが指摘としては正しい。
- **76-100**: 明確に妥当。実際にバグ・不具合につながる、または CLAUDE.md 等の明文化された方針に反している。

スコア **51 以上 → 「指摘通り」**、**50 以下 → 「修正不要」** とする(境界上でどちらとも言い切れない場合のみ「要検討」を使ってよい)。

「修正不要」と判定してよい典型例(`code-review` プラグインの false positive 例をベースに、レビュー対応用に調整):

- 既にPR内の別コミット、あるいはレビュー後の変更で対応済み
- 指摘者自身が後続のコメントで撤回・納得している
- Lint / 型チェック / CI で自動的に検出・修正される類の指摘(フォーマット、未使用import等)
- 意図的な設計判断であり、履歴(コミットメッセージ・過去のPR議論)がそれを裏付けている
- CLAUDE.md や既存の合意された方針に明記されていない、単なるスタイルの好み
- 指摘対象の行がそもそも今回のPRで変更されていない(スコープ外)

「指摘通り」とすべき典型例:

- 実際にバグ・不具合を引き起こす(ロジック誤り、null/undefined処理漏れ、境界値の誤りなど)
- CLAUDE.md や既存コードの一貫したパターンに明確に反している
- テストやエラーハンドリングの欠落など、実装方針として明らかに必要な対応が抜けている

## Step 5: 表形式で出力

以下のテンプレートで Markdown 表を出力する。GitHub へは自動投稿しない(ユーザーから明示的に依頼があった場合のみ `gh pr comment` 等での投稿を検討する)。

```markdown
# PR #NUMBER レビュー指摘の判定

| # | レビュアー | 場所 (file:line) | 指摘内容(要約) | 判定 | 理由 |
|---|-----------|------------------|----------------|------|------|
| 1 | @reviewer | src/foo.go:42 | 〜という指摘 | 指摘通り | 〜のため対応が必要。CLAUDE.md の「〜」に反する。 |
| 2 | @reviewer | src/bar.go:10 | 〜という指摘 | 修正不要 | 〜はすでに別コミットで対応済み。 |

## サマリ
- 指摘通り: X件(対応が必要)
- 修正不要: Y件
- 要検討: Z件(あれば理由と共に列挙)
```

- 指摘内容の要約は原文の意図を変えない範囲で簡潔に(1〜2文)。
- 「理由」には具体的な根拠(ファイル:行、CLAUDE.md の該当箇所、コミットSHA等)を可能な限り含める。
- 「指摘通り」の件について、対応が必要な場合は表の後に簡単な対応方針・優先度を添えてもよい。
